# 存档接入

`ULxGameInstanceSubsystem`（游戏实例全局子系统）持有 `ULxSaveManager`（存档管理模块）。管理器读取文件、按标签索引数据，并统一保存。角色和交互对象上的组件只做属性转换、查询与恢复，不单独读写文件。

## 保存范围

| 对象 | 保存属性 |
| --- | --- |
| 玩家 | 存档标签、背包容量与槽位、装备槽位、物品数量与实例词条、任务系列/任务标签与状态、职业标签/等级/经验/升级权限 |
| 机关 | 对象标签、功能节点 GUID、交互状态、机关开关状态 |
| 宝箱 | 对象标签、功能节点 GUID、交互状态、物品 ID 与数量、槽位位置、是否已经通知领取完成 |
| 商店 | 对象标签、功能节点 GUID、交互状态、有限库存商品的槽位位置、商品 ID 和剩余数量（包含售罄的零数量） |
| 仓库 | 对象标签、功能节点 GUID、交互状态、物品 ID 与数量、槽位位置 |
| 固定刷怪点 | 刷怪点标签、存活怪物的实际角色类与该类数量；普通怪物和首领按实际类分别记录 |

空槽和物品排列会保留；对象指针、界面、角色位置和其他未列出的战斗数据不进入记录。物品和职业的静态定义通过标签重建。交互中的临时占用状态恢复为可交互，不恢复旧会话。

仓库、宝箱和商人的物品均按预设物品处理，读档时从物品 ID 重建当前配置中的词条等静态属性，不保存实例词条。商人无限库存商品、售价倍率和收购倍率使用当前配置；只有有限库存的剩余数量进入有效存档数据。旧交互档仍可读取，按 ID 和数量迁移，旧价格与实例词条不再恢复。玩家自身背包和装备的完整物品存档保持原有行为。

四类交互对象的数据全部属于**地图存档**。正式会话保存时，`ULxSaveProfileStore`（多存档仓库）将交互记录保留在所选地图快照中，角色独立文件仅包含该角色记录。同一角色选择另一份地图档时使用另一份交互进度；不同角色进入同一份地图档时共用仓库、宝箱、机关和商人库存进度。

## 编辑器配置

1. `ALxPlayerCharacter`（玩家角色）已经自动挂载“玩家存档”组件。默认使用 `CharacterIDTag`（角色ID标签）；需要区分同类型的多个玩家时，在组件上设置不同的 `SaveID`（存档ID标签）。
2. 在关卡实例的 `ULxInteractableComponent`（交互提供组件）中设置 `InteractionIDTag`（交互对象ID标签）。建议使用类似“存档.交互对象.村庄.宝箱一”的 Gameplay Tag（游戏玩法标签）。同一份地图档内，跨关卡的交互对象标签也必须唯一且长期保持稳定；不同地图档可以使用相同标签。
3. 包含机关、宝箱、商店或仓库功能的交互组件会自动创建“交互存档”组件。每个交互功能使用资产内原有节点 GUID 定位，调整节点显示顺序不会串档；重新创建节点会产生新的身份。
4. 在项目设置的“游戏设置 / 存档”中配置 `SaveSlotName`（存档槽名称）和 `SaveUserIndex`（存档用户索引）。默认槽为 `LxARPG_AutoSave`，Windows 本地开发运行时位于项目的 `Saved/SaveGames`。
5. `ALxAISpawnPointActor`（固定刷怪点）已自动挂载“固定刷怪点存档组件”。在关卡实例上设置稳定且唯一的刷怪点标签；组件始终使用所属刷怪点标签，忽略基类中的显式 `SaveID`（存档ID标签）。读档按实际角色类重建存活数量，不恢复怪物位置、生命值、等级或其他实例属性。

未配置有效ID的对象会记录警告并跳过持久化；重复ID会拒绝后注册的对象。动态生成的交互对象需要由生成者分配可重复使用的稳定标签，本模块不负责重建已销毁的场景对象。

总关卡现有的仓库、宝箱、药剂商人和大门实例已分别配置 `存档.交互对象.总关卡.仓库一 / 宝箱一 / 药剂商人一 / 木门一` 标签。标签保存在各实例的世界分区外部对象包中，不设为蓝图共享默认值。`Source/LxARPGEditor/Scripts/配置交互存档.py` 默认只检查这四个实例；显式传入 `-ApplyInteractionSaveIDs` 才先备份再补齐空标签并保存，已有不同标签不会被覆盖。新放置或复制的实例仍须配置独立标签。

`LxARPG.Save.InteractionMapPIEPersistence`（实际地图交互存档回归）会连续运行两次真实总关卡，检查正式保存入口、地图磁盘快照、停止运行时的自动保存和重新进入后的自动恢复；机关同时检查状态值与门扇网格体的实际姿态。此用例不会替场景补写标签，必须使用 `-LxMenuSavePrefix=LxMenuSmoke_<32位随机GUID> -LxMenuIgnoreLegacy` 隔离玩家存档；退出后清理该次测试文件。

玩家、交互对象、固定刷怪点分别拥有独立标签索引，同一标签在不同索引空间中不会互相覆盖。同一份存档内的刷怪点标签仍须跨地图唯一。空怪物列表也是有效记录，读档不会因为数量为零而误认为首次生成；不含刷怪点字段的旧存档会保留原有玩家和交互数据，并将刷怪点索引初始化为空。

## 生命周期与蓝图接口

- 子系统 `Initialize`（初始化）在静态数据管理器就绪后发出“加载存档事件”，同步完成加载。独立游戏和 PIE（编辑器中运行）都早于玩家查询存档。
- 玩家默认数据初始化结束、交互功能树初始化结束后，存档组件注册并恢复对象自身数据。首次启动无存档时保留默认配置。机关状态监听在绑定后立即补发当前状态，确保晚于组件读档的蓝图开始运行事件也能同步门、开关的实际表现。
- `OnWorldBeginTearDown`（世界开始拆除）在对象清理前采集状态并发出“保存存档事件”。普通切图保留内存中其他地图的数据。
- 流式关卡卸载前缓存其对象；玩家和交互组件也在业务模块结束之前缓存并注销。对象清理后的空数据不会再次覆盖快照。
- 子系统 `Deinitialize`（反初始化）最终只落盘缓存，不再访问已清理对象。
- 蓝图可通过“获取存档管理模块”查询“存档是否已加载”，通过子系统的“请求保存存档”主动保存，并监听“存档加载完成 / 存档保存完成”的成功结果。启动事件早于场景蓝图，场景就绪后请查询状态。
- “请求加载存档”是幂等操作，已经加载时不会从磁盘回滚当前游戏进度；正式会话使用主菜单选定的角色档和地图档，旧单槽入口仍可用于兼容，不提供运行中直接替换管理器存档槽。

本地存档只采集权威对象；联机客户端不以自身副本覆盖服务端进度。多玩家若共享同一管理器，需要配置不同玩家存档标签。

## 文件与异常处理

文件包含格式标识、封套版本、数据长度、CRC 校验码以及引擎 `USaveGame`（存档对象）序列化结果，应通过本模块加载，不直接调用通用“从槽位加载游戏”。坏档、截断数据和不支持的版本会加载失败，自动保存不会覆盖原文件。写盘失败会保留内存数据并回报失败。

角色恢复先校验背包、装备、任务、职业四类数据；物品配置缺失等错误会阻止注册，保留原存档。恢复使用专用属性接口，不走接取/提交任务、领取宝箱、学习职业或增加经验流程。装备及职业效果由现有模块刷新来源效果，不把运行时效果对象存进文件。

刷怪点同样通过独立快照采集。管理器只提交当前刷怪点标签对应的数量记录，失败时保留旧快照并阻止落盘；不会提交该回调意外写入的玩家、交互或其他刷怪点记录。怪物蓝图类删除或重命名后，应保留可解析的软类路径或重定向，避免原数量记录无法恢复。
